# Database Design and Operations

PostgreSQL 17, database **`aircraft_predict_db`** (configurable with `DB_NAME`; `aircraft_app` is protected and
refused everywhere), schema `public`. EF Core Code First migrations in
`Backend/src/AFP.Infrastructure/Persistence/Migrations` are the schema authority; reference data comes from CSV
seeds (`tools/db/seed`). Naming is snake_case (EFCore.NamingConventions). **This document is the contract between
the ASP.NET Core API and the Python ML subsystem**; column names below are the exact physical names.

## Conventions

* Timestamps are `timestamp with time zone` holding UTC (`*_at_utc`, `*_utc`). The API rejects/normalises non-UTC input;
  telemetry timestamps must carry `Z` or an explicit offset and are converted to UTC on import.
* Enumerations are `varchar(32)` holding the PascalCase enum name (e.g. `UnderMaintenance`) — **except** the lifecycle
  status, which is an integer foreign key (below).
* JSON payloads are `jsonb`. Keys/values: `uuid` (application-generated) or `bigint GENERATED BY DEFAULT AS IDENTITY`
  for high-volume tables (`telemetry_record`, `aircraft_anomaly_result`, `action_audit`, `auth_audit`, `telemetry_rejected_row`).
* No hard-coded reference data: fixed sets are C#/Python enums; shared lists live in seeded tables.

## Four separate kinds of "status"

| Concept | Where | Values |
|---|---|---|
| **Lifecycle status** | `status_id` (int FK → `status`) on every table | 0 Inactive, 1 Active, 2 Deleted |
| **Operational criticality** (rule-based) | Domain rule `OperationalCriticalityRule` (not persisted yet — see open decision) | Normal, Critical, HighCritical, Unclassified |
| **ML risk category / prediction state** | `aircraft_risk_prediction.risk_category` (FK → `risk_status`), `.prediction_state` | Low/Elevated/High/Undetermined; Scored/InsufficientTelemetry/MissingFeatures |
| **Anomaly investigation** | `aircraft_anomaly_result.investigation_status` | New/Acknowledged/Investigating/Dismissed/ConfirmedIssue |

Operational status of an aircraft (`aircraft.operational_status`: Available/UnderMaintenance/Grounded) and workflow
statuses (work orders, imports, pipeline runs, models) are business states and remain separate from lifecycle status.

### Lifecycle status (`status` table)

| Column | Type | Notes |
|---|---|---|
| `status_id` | `integer` PK, not generated | Stable IDs from `tools/db/seed/csv/status.csv`; mirrored by the C# enum `LifecycleStatus` (a unit test fails if they diverge) |
| `name` | `varchar(32)` unique | Inactive, Active, Deleted |
| `description` | `varchar(256)` | |

Every other table (21) has `status_id integer NOT NULL DEFAULT 1` with `FOREIGN KEY → status(status_id) ON DELETE RESTRICT`
and an index (EF creates one per FK). **No exceptions**: append-only tables (audit, telemetry, revoked tokens) also carry it,
always `Active` today, so that a record can later be retired/soft-deleted without physical deletion. The default
`Active` is the business rule for every newly created row (the API always sends the value explicitly; the DB default
serves ML inserts). ID 0 is safe because IDs are never generated (no identity/sequence on `status`).
Soft deletion (`2 Deleted`) is distinct from physical deletion; status rows cannot be deleted while referenced.
No API endpoint performs soft deletion yet.

How to read prediction results: no row for an aircraft = **no prediction available**; `prediction_state =
InsufficientTelemetry` = stale/insufficient telemetry; `MissingFeatures` = required features unavailable;
`Scored` + `basis = DescriptiveIndicator` = rule-based summary of anomaly activity; `Scored` + `basis = Model` =
supervised model output (probability only if validated). **No eligible model** is reported by
`GET /api/v1/predictions/metadata` (`activeFailureModel = null`, `failurePredictionStatus`). Anomaly scores live only in
`aircraft_anomaly_result`.

## Database roles (least privilege)

Role names come from the root `.env` (defaults shown) and are distinct from any other database's roles.

| `.env` key | Default role | Privileges |
|---|---|---|
| `DB_USER` | `afp_predict_owner` | Owns database + schema. Used **only** for migrations and reference seeds. |
| `DB_APP_USER` | `afp_predict_api` | SELECT/INSERT/UPDATE/DELETE on application tables; no DDL; cannot modify `__ef_migrations_history`, `status`, `risk_status`. |
| `ML_READER_USER` | `afp_predict_ml_reader` | SELECT on `aircraft`, `telemetry_record`, `maintenance_log`, `model_version`, `pipeline_run`, `aircraft_anomaly_result`, `aircraft_risk_prediction`, `risk_status`, `status`, `health_threshold` (BR-01 limits for breach-count features). The ML roles are explicitly denied `telemetry_import` (defence-in-depth REVOKE); the telemetry simulator confirms ETL publication through the API CLI instead. |
| `INGEST_USER` | `afp_predict_ingest` | Spark ETL only: SELECT `aircraft`/`status`/`telemetry_import`; INSERT `telemetry_record`, `telemetry_rejected_row`, `action_audit`, `telemetry_import`, `pipeline_run`, `aircraft` (placeholders); DELETE own rejected rows on re-processing; UPDATE only `aircraft.last_telemetry_at_utc/updated_at_utc`, import status/count columns and run bookkeeping columns. No users, roles, tokens, auth audit, work orders, flags, models or predictions. |
| `ETL_WRITER_USER` | `afp_predict_etl_writer` | Member of the reader role, plus INSERT on `aircraft_anomaly_result`, `aircraft_risk_prediction`, `model_version`, `pipeline_run`; column-restricted UPDATE on `pipeline_run` (run fields) and `model_version` (`status`, `registered_at_utc`, `metrics`, `notes`). A trigger refuses any status other than Trained/Registered from this role. |

ML roles have no access to users, tokens, security/business audit, work orders, inspection flags, imports or thresholds.

## Isolation safeguards (`aircraft_app` is never touched)

| Layer | Guard |
|---|---|
| API startup | Connection resolved from `.env`/config and validated: database must equal `DB_NAME`, never `aircraft_app` or `DB_FORBIDDEN_NAMES`; target logged as `user@host:port/db` (no password). |
| API runtime | `/health` runs `SELECT current_database()` and is Unhealthy if it differs from `DB_NAME`. |
| `dotnet ef` | Design-time factory applies the same validation before any migration command. |
| Scripts | `tools/db/DbCommon.ps1` `Assert-TargetDatabase` in provision/migrate/seed; `grant-privileges.sql` refuses `aircraft_app`. |
| Seed SQL | `seed.sql` raises an exception inside its transaction unless `current_database()` is `aircraft_predict_db` (or a disposable `aircraft_predict_db_test_*`). |
| ML | DSN database must equal `DB_NAME`, never protected names; `current_database()` verified after connecting. |
| Tests | In-memory provider; PostgreSQL tests create and drop only `aircraft_predict_db_test_<random>`. The API test host disables `.env` loading. |

## Setup (run in order, from the repository root)

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
# 0. Configuration: .env exists (copy .env.example and generate secrets if not)
# 1. Roles + database (prompts for the postgres superuser password; stops if the database already exists)
.\tools\db\provision-database.ps1
# 2. Review and apply migrations as the owner, then least-privilege grants
.\tools\db\apply-migrations.ps1
# 3. Reference data (status, role, risk_status, health_threshold) — explicit, idempotent
.\tools\db\apply-seed.ps1
```

After the first successful provisioning set `DB_AUTO_CREATE=false` in `.env`.

## Reference data seeds (CSV → SQL)

| Item | Location |
|---|---|
| Editable CSVs (one per dataset) | `tools/db/seed/csv/status.csv`, `role.csv`, `risk_status.csv`, `health_threshold.csv` |
| Dataset definitions (table, key, unique sets, typed columns) | `tools/db/seed/datasets.json` |
| Generated, committed SQL | `tools/db/seed/seed.sql` |
| Compiler | `Backend/tools/AFP.SeedSql` |

```powershell
dotnet run --project Backend/tools/AFP.SeedSql -- validate   # strict header/type/length/required/duplicate checks with file:line [column]
dotnet run --project Backend/tools/AFP.SeedSql -- generate   # deterministic (key-ordered rows, LF endings) upserts in one transaction
dotnet run --project Backend/tools/AFP.SeedSql -- check      # fails if seed.sql is stale (also enforced by a unit test)
.\tools\db\apply-seed.ps1                                    # the ONLY step that writes seeds to PostgreSQL
```

Rows removed from a CSV are never deleted from the database. Status IDs must never be renumbered. No failures,
predictions or other operational data are seeded.

## Backup and restore

```powershell
$pg = "C:\Program Files\PostgreSQL\17\bin"
# Backup (custom format) as the owner; prompts for the password
& "$pg\pg_dump.exe" -h localhost -p 5432 -U afp_predict_owner -d aircraft_predict_db -F c -f "D:\backups\aircraft_predict_db_$(Get-Date -Format yyyyMMdd_HHmm).dump"
# Inspect a backup
& "$pg\pg_restore.exe" -l "D:\backups\<file>.dump"
# Restore into a NEW, empty database (never over an existing one), e.g. aircraft_predict_db_restore
& "$pg\createdb.exe" -h localhost -U postgres -O afp_predict_owner aircraft_predict_db_restore
& "$pg\pg_restore.exe" -h localhost -U afp_predict_owner -d aircraft_predict_db_restore --no-owner --role=afp_predict_owner "D:\backups\<file>.dump"
```

Recovery: verify the restored copy (row counts, `/health` with `DB_NAME` pointed at it in a separate `.env`), then
switch `DB_NAME` deliberately. Re-run `apply-migrations.ps1` (grants) after a restore. Keep backups outside the
repository; they contain user records and password hashes.
